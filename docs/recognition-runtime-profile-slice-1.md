# Runtime-profile Slice 1: control-store schema only

This slice adds the three runtime-profile tables and their immutable storage,
cross-table constraints and exact schema validation. It does not implement an
enrollment ceremony, observation collector, runtime authentication, new operation
formats, writer authority or activation. Synthetic rows in schema tests exist only
to exercise constraints. The actual migration creates no challenge, profile or
runtime-authentication scope record.

The existing v2 installation fields keep their meanings: `target` and
`control_identity` are deployment observations. `target_identity()`, ordinary
`transaction()` / `_verify()`, and Slice H's device-only ceremony are unchanged.
No ordinary access installs or repairs an extension.

`runtime_profile_schema.definitions()` is the executable schema specification.
It defines `recognition_runtime_enrollment_challenges`,
`recognition_runtime_profiles` and `recognition_runtime_auth_bindings`, all their
PK/UNIQUE indexes, foreign keys, immutable UPDATE/DELETE/REPLACE protection and
cross-table insertion guards. Every unique-key collision is protected against
SQLite REPLACE, not just primary-key collisions. Paths receive lexical SQL checks
and canonical filesystem-path checks during validation; UUIDs and lowercase hashes
receive SQL constraints and digests/audit relationships are checked on read.
Device/inode values are canonical unsigned decimal TEXT, including values above
SQLite's signed INTEGER range. They are never converted through REAL or numeric
CAST. Raw JSON inode extraction preserves their exact decimal representation.
The explicit extension migration requires SQLite's JSON `->` operator (3.38+);
an unsupported engine rejects/rolls back rather than using a lossy fallback.
Timestamps are integer UTC seconds in the datetime-supported range. Expiry is
issued_at + 600; profile creation at or beyond expiry rejects.

SQLite binding/affinity can normalize an integer-looking input to its declared
storage type. These are storage constraints, not an enrollment request parser.
Future enrollment APIs must also reject boolean/coerced input types before SQL.

The explicit low-level installer requires an existing compatible control schema,
foreign keys enabled and a caller-owned transaction. Its savepoint makes DDL
rollback-safe even if its exception is caught. Repeating the low-level installer
on the exact installed extension is harmless; a partial/malformed extension is
rejected rather than repaired.

`administration.migrate_runtime_profile_contract()` additionally requires the
existing strict deployment identity, expected integer generation, explicit
operator/reason and NOT_ACTIVATED state. It retains control-then-target lock order,
advances generation, preserves deployment observations and target UUID, adds
`format=recognition-local-control-v3` and `runtime_profile_sha256=null`, revokes
primary/session/step-up/confirmation authority, invalidates effective approvals
and appends `runtime_profile_contract_migrated`. The target is not modified.
DDL, revocation, new binding and audit share one control transaction/savepoint.

The CLI action is `migrate-runtime-profile-contract` with existing explicit
`--target`, `--control`, `--key-file`, `--expected-generation`, `--operator` and
`--reason` arguments. No key is read/generated by this migration. It is not a web
route. The high-level ceremony does not silently repeat: after success v3 ordinary
access rejects with `runtime_profile_contract_not_enabled`. Inspect durable
binding/audit history through trusted read-only host tooling after a lost ACK.

**Operational consequence:** Slice 1 deliberately leaves all ordinary v3
administrative and execution access blocked at the binding loader. No existing
v2 operation is reinterpreted as runtime-portable. Production stays NOT_ACTIVATED.
Migrating an operational installation is a separate deliberate operator action;
this implementation does not perform it. Later slices must implement the separately
reviewed runtime boundary before v3 access can be enabled. Slice 1 must not be used
as an identity mismatch repair or as an activation procedure.
