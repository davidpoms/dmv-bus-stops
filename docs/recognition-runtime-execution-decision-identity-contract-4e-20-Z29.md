# 4e-20-Z29: crash-stable execution-decision identity review

## 1. Z28 blocker and result

[Z28](recognition-runtime-replacement-ownership-outcome-contract-4e-20-Z28.md)
identified missing crash-stable coupling between duplicate exclusion, the actual
target outcome and its control record. This review concludes **existing-storage
assessment B: one specific new durable primitive is required**. A stable existing
identifier can identify intent, but current runtime storage cannot durably express
its committed-effect outcome and complete control relationship.

No implementation or new target storage is invented here. Target coupling and
replacement outcome record are **UNRESOLVED**. The current model is unchanged;
the 120-second ceiling, ordinary strict identity checks, legacy formats and
production blocks remain mandatory. This is not a performance investigation.

## 2. Exact identity definition and existing candidates

Use the existing correlation pair **D = (`authority_id`, `authority_sha256`)** to
name one intended authority decision. `authority_id` is the canonical random UUID
generated by original `_body()`; `authority_sha256` is `digest(body)` under existing
canonical rules. The digest is outside the immutable body, avoiding self-reference.
This defines an outcome lookup identity, not a bearer credential or permission to
originate/adopt a replacement executor.

The original issuer constructs it after the exact one-use confirmation CAS, under
genuine owner reservations and fresh scope/consent validation. It becomes durable
only when the complete authority/genesis/audit transaction is confirmed committed.
An in-memory ID after unknown commit does not prove either persistence or absence.
No new request may choose a replacement ID to evade existing exclusions.

## 3. Durable duplicate fence

Current authority storage has PRIMARY KEY(authority_id) and UNIQUE operation_id,
writer_manifest_sha256, confirmation_sha256, body_sha256 and audit_sequence, with
immutable UPDATE/DELETE/REPLACE guards. Thus the current control store already
rejects another authority for the same operation/manifest. Attempt storage adds
UNIQUE(authority_id), but cannot substitute for operation-level fencing.

Required correlation/exclusion domain is authoritative installation/target plus
logical operation ID, with exact operation and manifest digests; the manifest
must also remain excluded against substitution as another operation. Current
control uniqueness is stronger locally because one enrolled control store scopes
the installation/target. A request/attempt/session/profile/generation/activation
change cannot erase a previous operation/manifest conflict. Changed identity or
restore lineage must fail closed, not create a fresh uniqueness domain silently.

| Attempted action | Inspect and enforce | Rule |
| --- | --- | --- |
| First execution | Current exact D, consent/exclusions/claim graph, genuine original owner and target preconditions | Identity lookup alone permits nothing; existing writer gates still reject unsupported runtime authority |
| Same decision after crash | Exact authority and audit/consumption history, attempt/target metadata, any valid actual effect/outcome evidence | Historical inspection only; no restored live continuation or automatic execution |
| Retry after confirmed failure | Exact durable failure, original D and global operation/manifest exclusions | Reject execution retry under this contract; known rollback is not consent to reuse D |
| Retry after confirmed success | Exact correlated target proof and control recording, if available | Reject; no duplicate business effect or new grant |
| Retry after uncertain commit | All durable evidence for D under validated target/control identity | Remain blocked; absence of result or expired grant does not permit retry |
| Competing process/ceremony | Database reservation plus exact durable operation/manifest/confirmation fences and current scope | One original decision only; new authentication/UUID cannot adopt or substitute |

These conservative rules preserve current exclusion. They do not assert a complete
replacement execution fence exists. Inspection must validate identity/schema and
graph before trusting rows. A restored/copied database may be a different lineage;
absence there cannot prove the original decision did not commit. No new restore
policy, automatic fence release or cross-store recovery permission is defined.

## 4. Target outcome coupling

Current target storage can durably expose TARGET_ENTRY_CREATED keyed by attempt,
with operation/authority/manifest uniqueness. That marker references D, but is
explicitly metadata only. It neither says business mutation started nor proves
success/failure. `recognition_private_operations` and family records can show
manifest effects under the historical writer; they do not bind a replacement
runtime D/consent/incarnation to an atomic execution outcome.

Legacy claims/seals and production receipts have their own exact operation/claim/
approval formats and writer authority. They cannot be relabeled or synthesized
to provide replacement-runtime evidence.

| Outcome distinction | What current evidence can establish for replacement D |
| --- | --- |
| Mutation not attempted | Original live owner may know it did not enter DML; absence of an inert marker or row in a later snapshot is not a durable crash-stable proof |
| Mutation failed before commit | Confirmed rollback can resolve that original live transaction, but no current replacement D outcome journal records a durable terminal failure |
| Mutation committed | Manifest effects may be observable, but current runtime marker alone cannot prove a D-bound committed outcome |
| Mutation uncertain | Missing, partial, unavailable, wrong-lineage or conflicting evidence remains UNKNOWN; not success or safe retry |

**Target outcome coupling keyed by D is UNRESOLVED.** A valid future primitive
would need an authenticated/validated target-local decision outcome committed
atomically with the entire permitted family mutation and matching duplicate
exclusion. This states the necessary property, not a new table, column set,
codec, lifecycle event or DML instruction. Nothing is inserted in this slice.

## 7. Exact fail-closed uncertain-commit protocol

1. Original manager poisons the live owner, destroys usable permits and publishes
   no usable success if commit/cleanup/publication is uncertain. Never automatically
   retry a commit as if it were a new execution request.
2. A trusted authenticated **read-only inspector**, not an executor reconstructed
   from rows, selects the expected installation/target/operation and D. It opens
   only the intended validated identities/lineage and checks schema, canonical
   authority/digest/consent/audit, operation/manifest scope, claim/attempt/entry and
   available effect evidence. No key contents or credentials belong in output.
3. Control exclusion remains in force regardless of missing result, grant expiry,
   new process or new ceremony. Failure to inspect either store preserves UNKNOWN.
4. Declare target committed only with complete validated decision-bound evidence
   atomically coupled to actual effects on the intended target. Declare control
   completed only with corresponding confirmed control recording of that proof.
   Current replacement storage cannot meet those criteria: coupling UNRESOLVED.
5. Declare definitive failed/no-effect only with authoritative positive evidence
   resolving that exact attempt's outcome and excluding any concurrent/in-flight
   commit on the same lineage. Original confirmed rollback resolves only its own
   known transaction. Missing row, absent marker, process exit, timeout or stale
   snapshot alone is insufficient. A future durable no-effect rule is not invented.
6. Conflicting, unavailable, wrong-target/restore-lineage or incomplete evidence
   stays indeterminate. **An indeterminate decision cannot be retried under this
   contract.** Inspecting facts does not authorize record repair, completion DML,
   retirement or replacement execution.

Current `inspect_issuance()` already treats consumed confirmation without an exact
authority as UNKNOWN and reports `retry_authorized=False` and
`execution_authority=False`. That is useful denial behavior, not a target-outcome
inspector or proof that the missing primitive exists.

## 8. Retry and adoption rules

| Case | Exact rule |
| --- | --- |
| Same-decision retry | Reject executable reuse of D after original live owner is spent/lost; permit existing read-only historical inspection only |
| New-decision retry | New UUID, consent, session, generation or incarnation cannot evade existing operation/manifest conflicts; no new-decision retirement/retry policy is approved |
| Cross-process recovery | Read facts only; cannot recreate original PID/thread/context/reservations/permit |
| Cross-ceremony recovery | Fresh authentication authorizes inspection, not adoption of another ceremony's authority |
| Stale identity | Reject changed scope/digest/target/lineage; never refresh D's body or silently select a newer match |
| Expired identity | D remains historical and excluded; only its executable authority expires. No TTL deletes/reuses the fence |
| Duplicate identity | Exact read returns same history; conflicting body/digest rejects; immutable replacement/update/delete forbidden |

Expiry and failed execution do not themselves define a genuinely new decision.
New independently approved logical work must satisfy all current exclusions;
corrections remain explicit rather than destructive rewriting or stale retry.

## 9. Atomicity and coupling analysis

SQLite local transactions can atomically resolve the control decision group or
the target family mutation, not both databases as one commit. Ordering alone
does not establish coupled outcomes:

- Control first: durable D can remain with no target effects after a crash.
  It must exclude duplicates without authorizing another process to adopt it.
- Target first: effects can be committed while the control outcome is missing.
  Without a D-bound target proof/fence, another request or reader cannot safely
  distinguish committed execution from a recoverable failure.

The required primitive is a **decision-bound durable outcome journal** as one
logical security primitive: control exclusion/decision history, a target-local
commit witness atomic with effects and duplicate fencing, and exact control
outcome correlation. These are necessary aspects of one property across two
stores, not one table or a claim of atomic co-commit. Current codecs/readers do
not define them for replacement D. Target storage and the permitted recording/
inspection transitions remain **UNRESOLVED**; no new target record is invented.

A legitimate protocol could expose explicit incomplete recording/UNKNOWN rather
than instantaneous simultaneous completion. It must never publish completed
success before confirmed target proof and required corresponding control recording.
It must retain exclusions through uncertain prefixes, identity/restore changes
and result loss. This review defines the obligation but cannot claim the current
model implements or safely expresses that journal.

D is an **outcome/duplicate-correlation primitive, not an authorization substitute**.
Possession, correct syntax or a valid immutable row cannot bypass any of:

| Gate | Mandatory independent current validation |
| --- | --- |
| Authentication | Genuine current owner/session/primary, MFA/auth epochs and expiry |
| Activation | Exact independently validated current incarnation |
| Approval/ACK | Current effective approval and complete exact proposal/ACK pairing |
| Emergency stop | Current stop and operation block state |
| Dependencies | Fresh authoritative dependency and required manifest/precondition checks |
| Physical identity | Actual strict host/path/device/inode/schema/fingerprint and enrolled scope |
| Claims/history/control | Full current graph/exclusions, exact actual writes, migration/profile/binding and audit integrity |
| Scope | Exact operation/manifest/install/target/generation/profile/owner/epochs; no replacement values |
| Reservations | Actual registered original PID/thread/context, connections/transactions/query mode/epochs |
| Authority expiry | Original paired clock and strictly earlier than all applicable consent/auth/authority deadlines; never restamp or renew |

No identity query issues a writer, supplies raw SQL or creates a process-local
capability. No historical outcome changes the current meaning of old claims,
authorities, inert attempts, target metadata or legacy receipts.

## 11. Existing-storage assessment B

One specific new durable primitive is required: the decision-bound outcome journal
in section 9, coupling immutable D and logical-operation/manifest exclusion to a
target-atomic committed-effect witness and corresponding control outcome.
Existing IDs provide naming and current control uniqueness, not this coupling.

The identity portion can use existing authority ID/digest and canonical scope.
The target proof and later control outcome portion cannot be expressed by current
runtime AUTHORIZED-only / ATTEMPT_CREATED-only / metadata-only contracts. Legacy
seals cannot fill that gap without a separately approved new authority model.
This is assessment B, not A and not a proof of universal impossibility (C).
Do not fabricate target storage, append unsupported events or implement a journal.
